# Conformance suite

The packages in this repository are ports of [Lark](https://github.com/lark-parser/lark) 1.3.1. This suite is how
they stay identical: it describes grammars, inputs, and the results Python Lark produces for them, as plain data.
The .NET, Rust and TypeScript test suites all run every case, so each port builds the same trees, with the same
token types and positions, and fails on the same inputs.

## Layout

| Path | What |
|------|------|
| `cases/*.json` | The cases with their expected results. Generated; don't edit. |
| `sources/upstream.json` | Cases extracted from Lark's own test suite. Generated by `tools/extract_upstream.py`. |
| `sources/examples.json` | Hand-written cases: Lark's example grammars, the Python and Lark grammars, and more. |
| `sources/codegen.json` | Hand-written cases for the tree shapes of code generation. |
| `grammars/` | Grammar files used by `sources/examples.json`. |
| `known-failures/<port>.txt` | Cases a port doesn't pass yet. |
| `known-failures/dotnet-shapes.txt` | Cases whose shapes the .NET source generator works out differently. |
| `tools/` | The scripts that produce the cases, and `shapes.py`, the reference shape analysis. |

## A case

```json
{
  "id": "examples-0000",
  "grammar": "?start: sum\n...",
  "options": {"parser": "lalr", "lexer": "contextual"},
  "tests": [
    {"input": "1 + 2", "expect": {"tree": {"data": "add", "children": [...], "meta": [0, 5, 1, 1, 1, 6]}}},
    {"input": "1 +", "expect": {"error": "UnexpectedToken", "line": 1, "column": 3, "token": {...}, "expected": [...]}},
    {"lex": "{\"a\": 1}", "expect": {"tokens": [...]}}
  ]
}
```

- `options` uses Lark's option names: `parser`, `lexer`, `start` (a name or a list), `ambiguity`, `priority`,
  `maybe_placeholders`, `keep_all_tokens`, `strict`, plus `regex_flags` (Lark's `g_regex_flags` as letters, such
  as `"i"`) and `postlex` (`"python_indenter"` for Lark's `PythonIndenter`). Options that aren't given have
  Lark's defaults. Positions are always propagated (`propagate_positions=True`).
- A case with `"grammar_error"` (`"GrammarError"`, `"LexError"`, ...) expects loading the grammar to fail.
- A test either parses `input` (with an optional `start`) or lexes `lex` (with an optional `dont_ignore`).
- A tree is `{"data", "children", "meta"?}`, where `meta` is the propagated position, present when Lark has one.
  A token is `{"type", "value", "pos"}`. `null` is a `maybe_placeholders` placeholder.
- Positions are `[start_pos, end_pos, line, column, end_line, end_column]`, counted in code points, as Python does.
  Ports that count in UTF-16 code units (.NET, JavaScript) or bytes (Rust) convert before comparing.
- An error has the Lark exception name, and for the unexpected-input errors the `line` and `column`, the
  `token` (for `UnexpectedToken`), the `char` (for `UnexpectedCharacters`), and the sorted, de-duplicated
  `expected` terminal names.
- `shapes` are the tree shapes that code generation types the trees with; see below.

## Shapes

The code generators give each rule and alias a typed node, and their visitors typed parameters, from the *shape* of
its trees: what can stand at each position among the children. `tools/shapes.py` defines the shapes. It works on the
BNF rules Lark compiles the grammar into, and follows what Lark's tree builder does with them, so it accounts for
filtered tokens, inlined `_rules` and `?rules`, aliases, templates, imports, placeholders and repetitions.

```json
"shapes": {
  "add": [{"kind": "single", "name": "sum", "members": ["add", "number", "sub"], "slot": "sum"}, ...],
  "order": [..., {"kind": "repeated", "name": "line", "members": ["line"]}, ...],
  "sum": "inlined",
  "expr": null
}
```

Each tree name maps to a list of elements, each one child (`single`), zero or one (`optional`) or any number
(`repeated`), whose `members` are what that child can be: tree names, terminal names, `#none` (a placeholder) or
`#any`. A tree's children match its elements greedily, in order. The `name` is what accessors and parameters are named
after, and the `slot` the `?rule`, all-aliased rule or `_rule` the child stands for, whose result type it gets when one
is mapped. `"inlined"` means the name never makes a tree, and `null` that its trees have no fixed shape.

`generate.py` computes the shapes of every case that loads, and fails when a tree Lark builds for it doesn't match
them. The Rust and TypeScript packages compute them from their own compiled grammars in their conformance runs. The
.NET source generator, which reads the grammar text, is compared too: it is coarser on the cases in
`known-failures/dotnet-shapes.txt`, but its shapes must still fit every tree.

## Regenerating

The cases come from Python Lark itself, so they are only regenerated when the suite changes:

```
pip install lark==1.3.1
pip download lark==1.3.1 --no-deps --no-binary :all: && tar xzf lark-1.3.1.tar.gz
python conformance/tools/extract_upstream.py lark-1.3.1     # refreshes sources/upstream.json
python conformance/tools/generate.py                       # refreshes cases/*.json
```

CI runs both and fails when the checked-in files differ from what Lark produces.

To add cases, add them to `sources/examples.json` (or a new `sources/*.json` file), with `grammar` or
`grammar_file` (a path relative to this folder, or `lark:<name>` for a grammar that ships with Lark), `options`,
and `inputs` (`{"input": ...}` or `{"lex": ...}`), then run `generate.py`.
